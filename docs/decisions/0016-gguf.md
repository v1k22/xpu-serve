# 0016: GGUF files

Status: **accepted on the experiment branch** · 2026-11-12

## Context

Most quantized releases of open models are GGUF files: one file holding the weights, the tokenizer's vocabulary and
the chat template, in the layout llama.cpp reads. A model is published in twenty or more variants of it (2 to 16 bits
a weight), and people know them by name. xpu-serve read none: it refused GGUF by name and asked for the original
checkpoint, of which `convert` makes its own q8 / q4 pack.

What a GGUF file is, for an engine that is not llama.cpp:

- **A weight is rows of blocks.** A quantized tensor is stored row after row as fixed-size blocks of 32 or 256
  columns, in one of about twenty layouts (ggml's quantization types). Q4_0, Q4_1 and Q8_0 are a code per weight under
  one scale per 32, which is what a pack's q4 / q8 with a group of 32 is. The K-quants (Q2_K to Q6_K) put 2 to 6 bit
  codes under small integer scales per 16 or 32 columns and one f16 per 256. IQ4 indexes a table of 16 unevenly
  spaced levels. IQ1 to IQ3 index tables of 256 to 2048 patterns of 4 or 8 magnitudes, with the signs apart.
- **A file name is an average.** `Q4_K_M` is 57 % Q4_K, 24 % Q6_K and 18 % Q5_K for Qwen3.5-4B; a "dynamic" file
  (`UD-...`) mixes up to fifteen types by tensor. Supporting a file means supporting every type in it.
- **The converter changed the checkpoint.** llama.cpp's converter renames every tensor, stores some transformed (for
  Qwen3.5: norm weights plus one, a decay as `-exp(A_log)`) and reorders others (the value heads of linear attention
  tiled where Hugging Face groups them, which permutes rows of five tensors and the columns of one).
- **The tokenizer is half there.** Vocabulary, merges and token types are in the metadata; the normalizer and
  pre-tokenizer are a name (`tokenizer.ggml.pre`) llama.cpp maps to code. The chat template is there in full, and may
  differ from the model's own (Unsloth edits theirs).

## Decision

- **A GGUF file is imported, not served.** `xpu-serve convert <file.gguf> <dir>` writes a pack: `config.json`,
  `tokenizer.json`, the chat template, the manifest and the weights under the names the model code asks for.
  Everything after that (`serve`, `run`, `bench`, the tests) reads a model directory as before, and the engine at run
  time knows weight formats, not GGUF. The import copies bytes and takes seconds.
- **Quantized tensors are kept byte for byte.** `DType::Block` is a weight in a block format, stored in the pack
  exactly as the file has it (a U8 tensor of its rows) and named by format in the manifest. Nothing is re-encoded, so
  the values are the file's, and the weight is the file's size. Only float tensors are transformed back.
- **What the file reordered, the graph follows.** Rows and columns of a quantized tensor cannot be permuted (a
  super-block of 256 columns shares its scale), so the importer writes `linear_value_head_order: tiled` and the
  Qwen3.5 decoder computes in that order, with two transposes of activations around the recurrence.
- **One decoder on the host, checked against ggml.** `quant::decode_blocks` gives a block's values with ggml's own
  operations; fixtures written by ggml's C code hold it to the bit for all 19 formats. `read_rows` reads a Block
  weight through it, so the CPU reference backend runs every format with no kernel of its own.
- **The device holds the same bits, regrouped.** A block interleaves codes and scales at offsets no kernel can load
  a vector from (blocks of 110 or 210 bytes), and scatters a column's bits by halves and quarters. At upload the
  backend moves each field into a stream of its own, aligned, with the codes in column order: a lane of a kernel then
  loads the 32 columns of a unit in one aligned read. No bit is added; the pack stays as the file.
- **A decoder per format, three kernels.** `Fmt<F>` says what a unit loads, how its codes or levels come out, and its
  scale. Over it: a GEMV for up to 8 rows that reads each weight once, the weight written out as f16 for oneMKL's
  GEMM beyond, and rows gathered by id. A K-quant code goes into a float's mantissa without an int-to-float
  conversion (as the q4 kernel reads a nibble); a codebook format's magnitudes come from a table on the device, its
  sign code's eighth bit from a popcount.
- **Formats a pack already has take its kernels.** Q8_0, Q4_1 and Q4_0 are rewritten at upload as q8 / q4 with a
  group of 32, the same values, and get every path those have (the matrix-engine GEMV of a speculative verify, the
  few-row kernel). Q4_0 pays a bias per group for it, a ninth more memory than its file.
- **An architecture is a file in the importer.** `src/convert/gguf/qwen35.cpp` and `gemma4.cpp` map metadata to
  `config.json`, names to names, and undo the float transforms, over a shared tensor layout (`layout.h`: the pack
  tensors each tensor of the file holds, a fused one cut into runs of rows, one the converter computed from the config
  checked and left out); an unknown architecture, tensor or tokenizer is refused by name.

## Alternatives considered

- **Re-encode into q4 / q8 at import.** Exact for Q4_0, Q4_1 and Q8_0 only. Everything else would be rounded a second
  time (to q4) or stored at 8 bits (every dynamic file of Qwen3.8-27B becomes 27 to 29 GB whatever its size). The
  offline experiment that sized this work did so and is where the two numbers come from.
- **Read the file in place, with no import.** The same kernels would serve it; what it needs beyond them is a model
  source that is not a directory (every loader takes one) and a tokenizer and config built in memory. The import
  writes those as files, which costs a copy of the weights and nothing else, and leaves the loaders alone. A
  `serve <file.gguf>` that imports into a cache would be a thin layer on top.
- **Kernels over the blocks as stored.** No upload pass, but unaligned loads of odd-sized blocks, and two lanes
  reading the same bytes for the two nibbles or four bit pairs a byte holds for different columns.
- **Permute the tiled tensors back at import.** Exact for row permutations, impossible for the output projection's
  columns under a K-quant or a codebook format.

## Consequences

Measured on an Arc Pro B60 with Qwen3.5-4B (the numbers are in the README's GGUF section):

- **All 22 files of unsloth/Qwen3.5-4B-GGUF run**, each in the GPU memory of its size (Q4_K_M: a 2.74 GB file, 2.54
  GiB on the device; Q4_0 takes 7 % more than its file). Imports take 2 to 6 seconds.
- **The import is exact**: the BF16 file gives the original checkpoint's answer on all 300 MMLU-Pro questions (mean
  shift of the answer's probabilities 0.001), and the tokenizer written from the file equals Hugging Face's on every
  one of 248,077 token ids.
- **The kernels keep the file's values**: against the same weights decoded to f16 as they are uploaded, 298 to 300 of
  300 answers are the same, mean shift 0.001 to 0.002 (eight files from 2 to 6 bits).
- **One row** (a decode step), in weights read per second over 2560 x 9216 matmuls, the q4 pack kernel at 394 G: Q2_K
  465, Q4_K 393, IQ2_XXS 385, IQ2_XS 375, Q5_0 369, Q5_1 359, Q3_K 353, Q5_K 346, IQ2_S 346, IQ3_S 336, IQ3_XXS 335,
  Q6_K 333, IQ1_M 272, IQ4_NL 269, IQ1_S 268, IQ4_XS 255. None is bound by memory: a smaller format is not a faster
  one, and decode speed follows these numbers (Q4_K_M 90 tok/s, our q4 pack 109, f16 44).
- **Several rows**: 130 to 165 G at 4 rows and 80 to 99 G at 8, where the pack kernels' matrix-engine GEMV holds
  300 G. Prefill is the dequantized weight through oneMKL, like a pack's: 4,100 to 4,200 tok/s against 4,500.
- **Accuracy is the file's**: same answer as f16 on 294 of 300 at Q8_0, 269 to 280 at 5 and 6 bits, 248 to 252 for the
  4-bit K-quants (our round-to-nearest q4 pack: 194), 180 to 198 at 3 bits, 55 to 142 for the 2-bit files.

Limits, each refused by name or stated in CLAUDE.md:

- Two architectures (`qwen35`: Qwen3.5, 3.6, 3.8 dense, text; `gemma4`: Gemma 4 E2B / E4B, text, and its assistant,
  `gemma4-assistant`, without the centroid head the file does not carry). A mixture of experts in a block format is
  refused: the expert kernel does not read one.
- A GEMV over a block format costs more with every row (no matrix-engine version), so a speculative verify over such
  weights is slow; past 8 rows the weight is dequantized for a GEMM, as a pack's is on a discrete GPU.
- Split files and big-endian files are refused.
