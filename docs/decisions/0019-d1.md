# 0019: d1, LFM3-VL read as a decision model

Status: **accepted** · 2026-11-13

## Context

`LiquidAI/d1-2B` answers System One questions with the text decoder of an LFM3-VL checkpoint (`model_type`
`lfm3_vl`, the decoder's config under `text_config`, its weights under `model.language_model.`; config.json names the
architecture `D1Model`). The decoder is LFM3's (decision 0013): 24 layers, 13 gated short convolutions, 6 full and 5
sliding attention layers, the head tied to a 128,000-row embedding. A vision tower and projector sit beside it. The
checkpoint ships its own Python code, which is the reference: `prompt.py` (the prompt, the option codes, the
read-out), `runner.py` and `attention.py` (a request's sequences and what their full-attention layers see),
`calibration.py` (the temperature).

A question is a ChatML user turn, the state then `QUESTION:` and the question, closed by the assistant header and the
empty thought LFM3's template writes (`<think></think>`). The answer is read at that last token: each option's best
logit among a few tokens (a choice's code with and without a leading space, a noul's `yes` / `Yes` / `YES` and `no`
/ `No` / `NO`, a score's digit), divided by the calibrated temperature (1.3374 for d1-2B), through a softmax. On the
full-attention layers the model does not read causally (`d1_attention: "set"`): it packs up to 16 questions
(`d1_set_size`) after one state, the state's tokens see every token, each question's see the state and themselves; the
convolution and sliding layers stay causal over the packed sequence. A lone question is the whole prompt read both
ways. llama.cpp's server reads one prompt per question, which is the reference at a set size of 1.

The weights, tokenizer and chat template are licensed under the LFM Open License v1.0, which allows commercial use
only below $10M annual revenue.

## Decision

- **LFM3's layers are shared builders, `lfm3::Decoder`** (as `qwen3_5::Decoder` serves Qwen3.5's language and
  decision models): the weight prefix is probed (`model.` or `model.language_model.`), `lfm3::text_config` reads an
  `lfm3_vl` config's decoder, and a full-attention layer is either causal through a KV slot or over the step's
  tokens in groups. The language model's step graph stayed node for node what it was.
- **d1 is a decision model of its own, `models/d1/`**, found by config.json's `architectures: ["D1Model"]` (with
  `model_type` `lfm3_vl` or `lfm3`; the omni variant is refused by name). Its vision tower is not loaded.
- **One program, one step a sequence**: the decoder with its full-attention layers in groups (sliding layers through
  their KV slot, convolutions through theirs, all reset for each sequence), then the final norm of the rows at the
  answer positions (an input `answer_rows`, one row per question a sequence can hold), output as `hidden`. The host
  takes each option's logits from the rows of the output layer (the embedding table) its tokens need: about two tokens
  an option instead of a 128,000-wide row per question, and logits rather than log-probabilities (the softmax over the
  options is the same).
- **The prompt is `prompt.py`'s, token for token**: the state as text or as `json.dumps(indent=2)` (`py_text` learned
  the indent), user text with a zero-width space after the first character of every special token in it (the
  tokenizer's added tokens marked special, which `PromptTools::special_tokens` now gives), the option codes of
  `d1_codes` (the names when every one is a letter, A to Z, then AA, AB, ...) taking the next free single-token code
  of the reference's fallback pool when one is not a token of its own or is taken.
- **Calibration as `calibration.py` reads it**: the temperature of the question's bucket (`noul`, `score:<levels>`,
  `choice:small|mid|large|inventory`) from `temperatures`, else `default`; d1-2B's `temperatures` is empty. The
  tables are for typed answers (spans, boxes, estimates, multiple choice), which the System One API does not have.
- **Questions packed after their state, as `attention.py` packs them.** A request's questions go up to
  `d1_set_size` (16) a sequence: the first tokenized with the state, as its lone prompt is, each further one on its
  own after `QUESTION:\n`; each question's answer slot is its last token. The full-attention layers read the
  sequence in groups, a new mode of the graph's Attention (`AttentionAttrs::grouped`, a fourth input of a group per
  token): the state is group 0, which sees every token and every token sees, the k-th question group k, which sees the
  state and itself. cpu-ref masks the keys, the SYCL backend in each of its three paths (the kernel per row skips a
  hidden key, the GEMM path's softmax gives it no weight, the fused kernel masks it in its tile); each is checked
  against an fp64 reference with planted masks (no groups, a state that sees only itself, questions that do not see
  the state). A lone question in its group sees its whole prompt, which is the reading the reference gives one.
- **The set size is a load option** (`DecisionLoadOptions::set_size`, `--set-size N`; the reference's `set_size=`
  argument): the checkpoint's own by default, 1 to read each question alone (llama.cpp's reading). The System One
  API has no field for it; any other decision model refuses one by name.
- **A pack longer than the session's context is refused** with its questions and its token count
  (`max_tokens_exceeded`). The reference neither splits nor refuses one (its token budget only batches requests), so
  a pack is never split here either: that would give other answers.
- **Refused by name**: missing or blank instructions, instructions that are media, a score of fewer than two levels or
  with levels that are not text, single-character option names outside ASCII (the reference tests them with Python's
  Unicode-wide `isalpha`), a choice with more options than single-token codes, an attention mode other than `set`,
  an unknown `d1_` key. Typed questions and media are not in the System One API this server speaks.
- **Nothing of the checkpoint is committed.** The tests write a tiny checkpoint in d1-2B's layout with a byte
  tokenizer of their own; parity reads a checkpoint's directory.
- The API's answer fields stay the System One API's: a score's `score` is the expected level, and `confidence` is
  TypeSafe's formula. The reference's own `system_one` reports the median level and the top probability.

## What was measured

Against the checkpoint's own code in float32 on the CPU (`tests/parity/decision/reference.py`), cpu-ref f32
(`decision_parity.cpp`), at the checkpoint's own set size (16) and at 1. `requests.json` has 16 requests: two added for
d1 (noul outcomes described in part, a score of ten levels, options named by letters; 18 questions about one order,
which make two packs, of 16 and 2); the reference refuses 5 (a question without instructions, a score of levels that
are not text), and so does the engine. Tokens equal on every sequence, the top option on every question:

| Checkpoint | Requests | Set size 16: largest probability difference | Set size 1 |
|---|---|---|---|
| tiny d1 (the released classes, 8 layers, window 16) | 11 answered (43 questions) | 9.4e-7 | 6.0e-7 |
| d1-2B | 11 answered (43 questions, 40 and 60 options among them) | 1.9e-6 | 1.2e-6 |
| d1-2B | `decisions25.json` (25 questions, one a request) | 6.0e-7 | 6.0e-7 |

Through the server on cpu-ref (`systemone_eval.py --reference`): the 25 test decisions, 25 of 25 accepted answers and
the reference's (a question at a time, before packing); the parity requests packed, 43 of 43 the reference's answers
within 1.9e-6, the same 5 refused. Planted: the full-attention layers made causal move the tiny checkpoint's
probabilities by up to 0.038 and change 2 answers (at a set size of 1); every token put in group 0 (questions that see
each other) moves them by up to 0.093 and changes 4 (at 16).

What packing changes: the reference at its default set size against itself at 1, on the 38 questions of
`requests.json` that share a request with others: probabilities move by up to 0.25, and 6 of the 38 answers change
(answers held at 0.56 or less at either size). A request of one question reads the same either way.

## Consequences

- A request reads its state once for up to 16 questions, so several questions cost about one prefill of the state
  and their own tokens; at `--set-size 1` each question reads the state again (llama.cpp's reading; other answers on
  requests of several questions).
- `convert` makes packs of a d1 checkpoint as of any decision model; the embedding table, read on the host for the
  answer tokens, is read through `quant::read_rows` whatever its format.
- Measured on the Arc Pro B60 a question at a time (README); packing there is not yet: attention in groups on each
  lowering, parity at set size 16, the latency of a request of several questions.
